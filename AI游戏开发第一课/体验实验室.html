WHY DEMO FIRST

为什么先做 Demo，而不是先写策划案

对新人来说，AI 开发游戏最大的价值不是「省程序员工时」，而是把「想法 → 玩家反馈」的距离从几个月缩短到一个下午。一个能上手玩的 30 秒 Demo，胜过十页描述。

好处 1

把争论变成试玩

「这个玩法好不好玩」吵不出结果。做成 Demo，每个人玩 30 秒，讨论立刻有了共同对象。

好处 2

把风险提前暴露

操作手感、规则漏洞、节奏问题，在 Demo 阶段改一次只要一句话；上线前才发现就是事故。

好处 3

把范围锁到最小

Demo 强制你回答「最小验证什么」。只验证一个问题，反而更容易找到真正成立的玩法。

好处 4

让创意被看见

新人没有项目背书时，一个别人能打开就玩的链接，比简历上任何一行字都有说服力。

但 Demo 不能证明一切。它能验证「这条规则是否产生预期的玩家选择」，不能证明留存、付费、量产品质。案例库里的每个项目都标注了它验证了什么、没验证什么——这是制作人看 Demo 的基本功。
FROM ZERO · 6 STEPS

从 0 到 Demo：六步走

以 Codex 桌面端为例（Claude Code 等同理）。每一步都给出可以直接复制的话术和你必须亲自做的验收。完成一步勾一步，进度存在你自己的浏览器里。

01

装好工具，建一个空文件夹

安装并登录 Codex 桌面端。在电脑上新建一个空文件夹，例如 我的第一个游戏。空文件夹是你的「项目」，AI 只在这里面读写文件。

✔ 验收：你能说出 AI 被允许操作的是哪个文件夹。

02

把文件夹关联进项目，让 AI 先读现状

在 Codex 里新建项目并选择这个文件夹作为主目录。第一条消息不要急着要游戏，先确认它看对了地方。

你正在处理一个网页小游戏项目，工作目录就是当前关联的文件夹。 先不要写任何代码。请告诉我：你能读写的目录是哪一个？目前里面有什么文件？

✔ 验收：它报出的路径就是你建的文件夹；如果它声称创建了文件而你没看到，直接追问。

03

发出第一条「最小可玩」需求

第一条需求只锁一件事：一个玩家动作 + 一个结果 + 一条验收链。不要说「做一个小游戏」。

请在这个文件夹里做一个可以用浏览器直接打开的单文件网页小游戏（index.html）： - 玩家用方向键移动一个角色； - 碰到星星得 10 分； - 一局 30 秒，时间到显示总分，可以重新开始。 完成后请告诉我文件路径，我自己打开试玩。不要增加商店、关卡、联网等任何其他功能。

✔ 验收：你亲自双击打开 index.html，确认能移动、得分、结束、重开——四项都亲手试过。

04

小步迭代：一轮只改一件事

改之前先复制整个文件夹做备份（例如 我的第一个游戏_30秒备份），再下修改指令。每轮只提一个改动。

只把一局的时间从 30 秒改成 45 秒，其他规则、画面、操作都不要变。 改完请确认：开局和重新开始后都是 45 秒。

✔ 验收：重开一局核对确实是 45 秒；顺便确认计分、结束、重开没有被顺手改坏。

05

出问题：用「操作 → 实际 → 预期 → 范围」反馈

发现不对时，先截图（Win + Shift + S），再把四要素写清楚。不说「有 bug，修一下」。

操作：开局后我碰到了第一颗星星。 实际：分数从 0 变成了 20（见截图）。 预期：每颗星星只加 10 分。 范围：只修复计分错误，不要改动其他任何规则和画面。

✔ 验收：修复后重玩，同一颗星星只加 10 分，其余行为与故障前一致。

06

留下制作记录，打包带走

让 AI 把这一轮的事实写成记录，下次接着改不用翻聊天记录。交付时复制整个文件夹并压缩成 ZIP。

这一轮先到这里。请在当前文件夹写一份「制作记录.txt」，列出：游戏入口文件、当前规则、本轮改动、我实际检查过的结果和未检查项、下一轮只做的一件事。不记录账号信息，不上传文件。

✔ 验收：把 ZIP 发给同事，对方不解压你的聊天记录也能直接打开玩。

走完六步你就已经超过了大多数「只聊不做」的人。下面的模拟工作台让你在没装 Codex 的电脑上，也能先把「下指令 → 试玩 → 验收」的肌肉记忆练出来。

CASE STUDY · 魔兽风 RPG 塔防

实操拆解：用 AI 做一个魔兽风 RPG 塔防

前面讲的是原则，这一节给你完整的一天半实操：假设你要做一个叫《峡谷守卫战》的塔防 Demo——英雄守峡谷口，塔的流派组合决定打法（魔兽 RPG 的味道来自英雄单位）。八轮指令，每轮都给出可以原样复制给 Codex / Claude Code 的完整话术、这轮结束你要亲手验收什么、以及制作人为什么这样切。这不是理想化剧本：案例库里 Dice Defense 三天五版的录屏，就是同一种节奏的真实记录。

先看纪律，再看话术：每轮只推进一个可验证闭环；每轮改完你亲自试玩；跑不起来就让它写 Not Run，不接受「应该可以」。
R0

立项：先砍范围，不动手

30 分钟 · 零代码

目标：把「魔兽塔防 RPG」缩成一句可验证的体验命题，并写清这一轮不做什么。

我想做一个魔兽 RPG 味的塔防网页 Demo，命题是：英雄守住峡谷口，塔的流派组合决定打法。 先不要写代码。请问准我 3 个问题，分别确认：玩家每一分钟在做什么操作、赢和输分别是什么画面、为什么英雄（而不是纯塔）是核心。每个问题给我两个选项，我回答后你整理成一页规则：玩家目标、核心循环、本 Demo 明确不做的内容（不做联网、不做抽卡、不做关卡编辑器）。

✔ 验收：你拿到一页纸规则，且「不做什么」比「做什么」更长——范围感是制作人第一课。

制作人批注：AI 最擅长顺着你说「都加上」。立项这一轮的唯一任务就是防止它把 Demo 做成大游戏。

R1

最小循环：一条路、一波怪、一座塔

第 1 天上午 · 对标 Dice Defense V0.1

目标：30 秒内能看到「怪沿路线走 → 塔自动攻击 → 怪死光或漏光 → 结算」完整转一圈。

请在当前文件夹做一个单文件网页塔防（index.html），Canvas 实现，最小循环： - 地图：固定一张，左侧入口到右侧基地的一条 S 形路线，路边 6 个可建造点； - 怪：只有一种，80 血，沿路线匀速走，到终点基地扣 1 命（共 3 命）； - 塔：只有一种箭塔，造价 50 金，射程 100，每秒 1 箭、每箭 20 伤害；开局 100 金； - 波次：只有 1 波 10 只怪；全部消灭显示胜利，命没了显示失败；可重开。 不要英雄、不要升级、不要第二种塔。完成后告诉我打开方法，我自己试玩。

✔ 验收：亲手打完一局——怪沿路线走、塔在射程内开火、胜利和失败两种结算都各看到一次。

制作人批注：第一版丑没关系。它存在的意义是验证「塔防循环成立」和「AI 能跑通整条链路」，不是好玩。

R2

波次与成长：数值进配置表

第 1 天下午 · 对标 V0.2

目标：从 1 波变 5 波，难度曲线写在一张表里，而不是埋在代码里。

在现有塔防基础上只改波次系统： - 改为 5 波，第 n 波怪物数量 8+2n，血量系数依次为 1 / 1.3 / 1.6 / 2 / 2.6，第 5 波最后 1 只为 BOSS（500 血、速度减半）； - 把以上数值写进文件顶部一个 WAVES 配置表里，逻辑代码只读表，不写死数字； - 界面显示「第 x/5 波」和下一波倒计时 3 秒。 禁改：塔的数值、路线、建造点。完成后逐波截图或列日志给我看每波实际刷出数量和血量。

✔ 验收：日志里 5 波的数量和血量与配置表一致；你完整打完一局，第 5 波 BOSS 明显不一样。

制作人批注：「数值进表」是团队协作的生命线——以后调平衡的是策划改表，不是求 AI 翻代码。SlimeSlots 案例的规则进 JSON 是同一个动作。

R3

塔流派：给玩家一个真选择

第 2 天上午 · 对标 V0.3

目标：三种塔形成打法差异——箭塔快单伤、炮塔范围、冰塔减速，各有三级升级线。

新增两种塔和升级系统，数值进同一个配置表： - 炮塔：造价 80，每 1.5 秒一发，范围 40 内群体 15 伤害；冰塔：造价 60，不造成伤害，命中减速 40% 持续 1.5 秒； - 每种塔可升 3 级，升级费用和数值曲线你在配置表里给出，原则是「升满级 ≈ 三座一级塔的价值，但占一个建造点」； - 建造点点击后弹出选择界面。 禁改：怪物路径、波次表、结算规则。完成后列出三种塔各级 DPS/效果对照表，并说明你用哪一局实测验证。

✔ 验收：分别用「纯箭塔」「炮+冰」各打一局，两局体验明显不同；配置表数值与实测一致。

制作人批注：这一步验证的是玩法命题本身——「流派组合决定打法」。如果两种打法打起来没区别，命题就不成立，后面的都别加。

R4

英雄入场：RPG 味道的来源

第 2 天下午 · 对标 V0.4

目标：一个可操作英雄 + 一个主动技能。英雄是「魔兽风」和纯塔防的分水岭。

新增一个英雄单位： - 点击选中、点地面移动（参考魔兽操作）；普攻近战 30 伤害/秒； - 主动技能 Q：对周围 120 范围造成 150 伤害，冷却 8 秒，界面有冷却转圈； - 英雄血量 600，死亡不判负，10 秒后在基地复活； - 英雄和塔的数值同样进配置表。 禁改：三种塔、波次表、基地生命。完成后告诉我：英雄操作、技能释放、死亡复活各怎么试玩验证。

✔ 验收：试玩三件事——Q 技能清一波聚团怪、英雄送死后 10 秒复活、英雄不在场时塔防仍能运转。

制作人批注：英雄「死亡不判负」是设计决策不是技术限制——它让玩家敢操作。这类决策必须你写进指令，AI 不会替你想到。

R5

经济闭环：让每一金币都有出处

第 3 天上午

目标：击杀得金、波次结算奖励、界面随时可见——经济是塔防的隐形主角。

只改经济系统： - 普通怪击杀 +8 金，BOSS +100 金；每波清完额外 +30 金； - 界面常显当前金币、本波已得金币； - 数值进配置表，并在结算画面显示本局总收入。 禁改：塔与英雄的战斗数值。完成后给我一局的经济流水日志（时间、来源、金额）。

✔ 验收：对照日志抽查 3 笔金币来源；打一局验证「攒钱升满一座塔」和「铺开两座新塔」两种花法都成立。

制作人批注：经济流水日志是验收经济系统的唯一可靠方式——看界面猜不出哪里漏算了。

R6

手感与表现：只动表现层

第 3 天下午

目标：弹道、血条、伤害飘字、命中反馈——让同样的数值「玩起来爽」。

只改表现层，一行战斗数值都不许动： - 箭塔/炮塔攻击加可见弹道（飞行 0.15 秒）；怪物头顶加血条； - 伤害以飘字显示（物理白色、技能金色），0.6 秒上浮消失； - 英雄 Q 技能加范围指示圈和释放闪光； - 音效用 WebAudio 合成的占位音，不引外部资源。 验收标准：改动前后各打一局第 3 波，怪物死亡时间点和总时长应完全一致——用日志证明表现层没有碰数值。

✔ 验收：两局日志的死亡时间戳一致；新表现全部在画面上亲眼看到。

制作人批注：方块英雄果酱印案例的同一条纪律——表现层只读结果。这条破了，以后每次美化都可能改坏平衡。

R7

验收与调平衡：制作人的收官动作

第 3 天晚上 · 对标 V0.5

目标：三局完整试玩记录 + 一次只改一个数的平衡调整 + 制作记录归档。

现在做验收，不改任何代码： 完整试玩 3 局并输出记录表：每局的流派选择、漏怪数、基地剩余命、剩余金币、英雄技能使用次数、第几波压力最大。 如果数据显示第 3 波明显压力断层，先只提一个最小调整方案（改配置表里的一个数），说明预期影响和验证方法，等我确认再改。

✔ 验收：三局记录表真实可核对；调整只动一个数；最后让 AI 写制作记录（入口、规则、改动、已验/未验项、下一步）。

制作人批注：「先给数据再提一个最小方案」是防止 AI 一口气把五个数值全改了——那样你永远不知道是哪一改起了作用。

完整进度：R0 立项 → R1 最小循环 → R2 波次 → R3 流派 → R4 英雄 → R5 经济 → R6 手感 → R7 验收。一天半，八轮，每轮都有证据。

对照真实证据：这套「一天两版、每版留证」的节奏不是编的——下方案例库里 Dice Defense 的 V0.1→V0.5 五段录屏就是真实发生的三天。拆解里的每条话术都可以直接复制去你自己的 Codex 项目里用。

PRODUCER WORKFLOW

制作人视角：Codex / Claude Code / Grok 怎么分工

给 AI 下游戏任务：五段式

目标

玩家看到什么变化

引擎

版本、入口、运行命令

约束

分辨率、性能、复用规则

验收

步骤、数值、截图时点

禁改

文件、模块、存档、资源

✕ 差提示（来自真实反例）

「把这个效果做得更好看。」

不知道改哪一层 · 不知道什么时候算完成 · 容易顺手改坏业务逻辑。

✓ 好提示（方块英雄真实需求改写）

「短促奶油爆破后，每个消除格出现 1 枚淡果酱印；约 0.55 秒消失。只改表现层。1080×1920 和长屏各截峰值、中段、结束三张图。」

可定位、可计数、可定时 · 有边界，也有截图标准。

六个最常见的坑，每个配一个纠偏动作

01 一次要做整款游戏先限定 1 个玩家动作 + 1 个结果 + 1 条验收链→ 纠偏：拆到能在 1–3 个可观察结果上验收，不能拆就继续拆
02 只写「更好看」AI 不知道改哪层、何时算完→ 纠偏：把层级、时长、透明度、分辨率和截图时点写清
03 生成了但没运行「页面打开了」不等于功能完成→ 纠偏：要求真实引擎构建 + 实际入口截图；跑不了就写 Not Run
04 只看开发自测自己生成自己说通过，没有说服力→ 纠偏：关键链路用独立 QA 或只读验证复跑一遍
05 资源与规则混在一起改表现时顺手动了胜负逻辑→ 纠偏：表现层只读结果，业务状态由领域逻辑拥有（方块英雄果酱印的关键设计）
06 只看单一尺寸电脑上好好的，手机上穿帮→ 纠偏：主基准 + 短屏/长屏 + Safe Area 各截一套
验收原则（背下来）：每一条策划规则，都要能映射到「画面、日志、快照或配置」中的一个证据。写不出证据的规则，就是还没讲清楚的规则。
PROMPT LIBRARY · 直接抄

场景话术库：六种常见情况，照着写就行

新人卡住往往不是不会想，而是不知道怎么开口。下面六类覆盖做游戏 Demo 90% 的场景，全部可直接复制改参数用。共同骨架都是五段式：目标 → 引擎 → 约束 → 验收 → 禁改。

场景 1 · 加一个新系统
为现有游戏新增【商店系统】：每波结束后可花金币买【3 种强化之一】。 约束：数值写进配置表；复用现有结算界面风格；不影响战斗中的操作。 验收：打完一波能看到商店，三种强化各买一次都生效，没钱时按钮置灰。 禁改：战斗数值、关卡流程。先列出要改的文件和影响，我确认后再动手。

要点：新系统先说「挂在哪个现有节点上」（每波结束），AI 才知道往哪接。

场景 2 · 调平衡数值
第 3 波难度过高：把配置表里第 3 波血量系数从 1.6 降到 1.35，只改这一个数。 改完跑一遍第 3 波，对比改动前后的基地剩余命，用日志证明只有这个数变了。

要点：一次只改一个数，并要求前后对比——否则你无法归因。

场景 3 · 修 Bug（四要素）
操作：英雄在冰塔减速区边缘反复横跳移动。 实际：减速效果偶尔不生效（见录屏/截图）。 预期：进入减速区 0.2 秒内必生效。 范围：只修判定逻辑，不改减速数值和表现。修完给我复测步骤。

要点：先截图再开口。「操作→实际→预期→范围」缺一个，AI 就只能猜。

场景 4 · 接美术资源
我放了一张 assets/hero.png（32×32，透明背景，人物居中）。 先检查：尺寸、透明通道、主体是否居中，报给我；确认没问题再把英雄占位方块换成它，锚点取图片底部中心。 禁改：碰撞体积、移动逻辑。验收：英雄贴地、转向正常、不遮挡血条。

要点：方块英雄案例的原话——先查透明与居中，原图哈希一致，再隔离接入。

场景 5 · 加手感 / 音效
只加表现：攻击命中时画面顿 2 帧 + 目标闪白；击杀播放 WebAudio 合成的短促上扬音（不引外部文件）。 一行战斗数值都不动。验收：改动前后同一波次的怪物死亡时间戳完全一致。

要点：手感改动的验收标准是「数值日志纹丝不动」——表现层只读结果。

场景 6 · 每日交付三件套
今天到此为止。请输出：① 当前可玩版本的打开方法；② 今天每轮改动清单和对应的试玩结论；③ 已知问题和 Not Run 项；④ 明天只做的一件事。写进「制作记录.txt」，不记录账号信息。

要点：目标不是「多写代码」，是每天有一个别人能复核的可玩状态：可玩 build + 30 秒录屏 + 变更说明。

创新思维：不只是更快地做旧游戏

AI 对游戏的价值分两层：生产提效让旧玩法更便宜（本课大部分内容），体验创新让过去不可能的玩法第一次成立。制作人两个都要想，但第二个才决定你能不能做出别人没有的东西。

世界即时生成

场景不再全部预制，玩家一句话就可能改变可探索空间。难点：持续一致、可设计、可控。

方向二

角色真正回应

NPC 记住关系、理解上下文并形成长期状态。难点：人设、剧情边界、成本与安全。

方向三

玩家成为共同作者

方向四

持续运营闭环

AI 帮制作人分析反馈、生成变体、做活动素材，但上线决定仍由人和数据把关。

验收四维：你的作业怎么被看

维度合格优秀
能跑文件发给任何人，双击就能玩，不需要你的口头解释换台电脑、解压到新位置，依然能跑
证据每轮改动有试玩记录或截图，不是「AI 说完成了」有日志/流水/前后对照等可复核的硬证据
边界指令里写了禁改范围，旧功能没被顺手改坏表现层与数值层分离，改美观不动平衡
记录有制作记录，别人能接手继续改记录里如实写了「未检查项」和已知问题
提交规范：文件夹命名 姓名_作业X_日期，完整压缩为 ZIP 后按讲师给的 SVN 路径提交（SVN 配置见第一节正课最后一关）。不要只交截图或聊天记录；不要把课堂预制矿工文件当作业；不要包含账号、密钥和公司内部资料。
